## Содержание

### Стек (учебный MVP)

| Блок | Вариант |
|---|---|
| Backend | Python + FastAPI |
| БД | PostgreSQL |
| Semantic search | Embeddings + LLM |
| Векторный поиск | pgvector |
| Frontend | React / Next.js |

### Гибридный matching

1. **Жёсткие фильтры** — категория, ЕИ, критичные характеристики, количество, состояние, география.
2. **Точные совпадения** — артикул, модель, производитель.
3. **Semantic matching** — разные записи одного товара (embeddings).
4. **LLM-проверка** — объяснение совместимости и аналогов.

**Match Score (веса):** артикул/модель 30%; тех. характеристики 30%; semantic 15%; цена 10%; география 5%; количество 5%; производитель 5%.  
90–100% — высокое совпадение; 75–89% — подтверждение; ниже 75% — не показывать автоматически или на проверку оператору.

### Где AI нужен

- Нормализация названий и характеристик.
- Semantic search и поиск аналогов.
- Автокатегоризация; в перспективе — неликвиды по истории движения.

### Где AI не нужен

- Фактические остатки и наличие (источник истины — ERP клиента).
- Платежи, комиссия, юридическое подтверждение, финальная совместимость критичных позиций — **бизнес-логика + человек**.

### MVP-поведение

- Human-in-the-loop: обе стороны подтверждают; AI не заключает сделку автоматически.
- Обратная связь (принял/отклонил/причина) — для обучения.
- На MVP важнее **Acceptance Rate**, чем абстрактный Precision.

## Ключевые наблюдения

- ИИ у NELIKVID, EME, BuildSave уже заявлен — отличие продукта не в «наличии AI», а в качестве данных двух сторон и экономике сделки.

## Принятые решения

- Matching **гибридный**, не end-to-end нейросеть.
- Синхронизированная копия остатков в Sansara; истина по наличию — у клиента.

## Обоснование

Снижает риск ошибочного подбора (например, кабель 3×2,5 vs 5×6 при похожих названиях).
